**数据线规格识别与质量检测：现成项目调研**

调研日期：2026-11-06。范围：连接电脑的 USB-A、USB-C、USB4 / Thunderbolt 线材，以桌面软件为主，商业测试仪作为功能与成本参照。HDMI、DisplayPort 独立线材、网线及 Lightning 专用检测不作为本轮重点。本报告依据项目仓库、作者文档、厂商官网与平台文档；尚未在实机上验证这些工具的准确率与兼容性。

已有接近需求的开源软件，尤其是 Apple Silicon Mac 上的 [WhatCable](https://github.com/darrylmorley/whatcable)、[CableScope](https://github.com/tzzs/cablescope)。Windows 有成熟的连接信息查看工具，也有新项目探索线材信息读取，但兼容性取决于电脑的 Type-C 控制器、固件及系统接口。本轮未发现能够跨 Windows / macOS / Linux、无需额外硬件、准确判定任意线材全部规格与电气质量的成熟通用成品。

产品应分别回答四个问题：线材声明支持什么、这次连接协商到了什么、在当前设备组合下实测表现如何、是否做过物理质量测量。这四类证据应分别展示，避免合并成一个没有依据的“质量分”。

| 用户想知道的事 | 纯软件能够提供的证据 | 不能据此直接得出的结论 |
|---|---|---|
| 现在的数据连接速度 | 操作系统提供的设备、端口、链路状态 | 当前只有 480 Mbps，不代表线材最高只能到 480 Mbps |
| 线材额定数据速度、功率等级 | 在兼容硬件上读取 e-marker 中的声明字段 | 芯片声明不证明实际信号质量或载流能力达标 |
| 为什么充电慢 | 平台开放时读取 PD 协商、适配器与电池状态，辅助定位限制因素 | 当前功率低，不足以单独认定线材劣质 |
| 是否掉线、是否稳定 | 当前连接的断连事件、可用错误计数、受控传输测试 | 不能仅据此排除端口、Hub、驱动或外设问题 |
| 是否断线、接触不良、电阻异常 | 软件可观察症状，无法通用地直接测量每根导线 | 需要导通/电阻测试硬件获得直接证据 |
| 是否通过某个高速等级的电气要求 | 普通电脑应用不能替代合规测试 | 需要相应信号完整性仪器、夹具与测试流程 |

上述边界可由三类一手资料交叉支持：微软速度接口区分设备“当前工作速度”和“支持的速度”；UCC3 厂商明确区分芯片信息读取与导通/电阻实测；USB-IF 线缆认证另设信号完整性与 PD 测试要求。[微软速度接口](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/usbioctl/ns-usbioctl-_usb_node_connection_information_ex_v2_flags)、[UCC3 官方说明](https://bit-trade-one.co.jp/adusbcim3/)、[USB-IF 认证说明](https://www.usb.org/cable_connector)。

以下是值得参考的软件与开源设计，优先级按与用户目标的贴近程度及 Windows 实用性考虑。许可证信息用于筛选代码复用候选，最终应以实际复用文件的许可为准。

| 项目 | 平台与形态 | 已核实能力 / 可借鉴点 | 状态与主要边界 |
|---|---|---|---|
| [WhatCable](https://github.com/darrylmorley/whatcable) | macOS 14+、Apple Silicon；菜单栏 + CLI | 读取 e-marker、PD 信息、USB/雷电连接状态，解释瓶颈，支持 JSON | 最直接的成品参考；有签名公证下载；默认 MIT，Pro 插件专有许可；端口和机型覆盖有限 |

| [usbutils / lsusb](https://github.com/gregkh/usbutils) | Linux/BSD；命令行 | 设备枚举、描述符、USB 拓扑与连接信息 | lsusb 为 GPL-2.0-or-later；通用基础工具，不是线材质检成品 |
| [usbeehive](https://github.com/abrauchli/usbeehive) | Linux；Rust CLI/库 | USB、Type-C、PD 信息采集与解析，JSON/watch | MIT；取决于内核/驱动暴露的 sysfs；合同功率上限不能直接称为实际充电功率 |
| [alvarop/usb_c_cable_tester](https://github.com/alvarop/usb_c_cable_tester) | KiCad 独立硬件设计 | 线材两端插入板卡，通过 LED 看导线连通情况 | README 标 CC BY 4.0；需要制板/硬件，不能接电脑同时使用；不含高速性能认证 |

WhatCable 最值得先体验。免费部分已经覆盖识别与解释，Pro 采用免费核心加付费功能模式；README 标价 £9.99 一次性、最多 2 台 Mac，增加实时功率、历史和进一步诊断等功能。其 v1.5.0 把线阻估计明确标为实验性，不能当作经过仪器校验的线阻结果。许可证也有边界：根目录默认 MIT，独立目录许可可覆盖该默认，Pro 插件为专有代码。[README](https://github.com/darrylmorley/whatcable/blob/main/README.md)、[v1.5.0 发布说明](https://github.com/darrylmorley/whatcable/releases/tag/v1.5.0)、[LICENSE](https://github.com/darrylmorley/whatcable/blob/main/LICENSE)。

单头插线能否识别，也已有直接经验可参考：WhatCable 作者说明，有些 Mac 会读取悬空线材的 e-marker，有些需要另一端接充电器、扩展坞或其他真实设备才能触发。第一版不能承诺“所有数据线插一头就能鉴定”；也不能把“没有读到 e-marker”直接解释为没有芯片、低速线或坏线。[WhatCable 限制说明](https://github.com/darrylmorley/whatcable#caveats)。

Windows 候选需要特别审查实现状态。UsbScope 的驱动 `Driver.c` 仍把 UCSI 连接器数量、能力和身份响应留为空，公开 README 中提到的 e-marker/PD 目标不代表已经实现通用读取。WhatCable 的 Windows 项目则明确是研究性质的兼容性 checker，启用测试接口的选项会修改设置并重启设备；不能把它当作无副作用的普通扫描器。[UsbScope 驱动源码](https://github.com/Kenshin9977/usbscope/blob/main/src/UsbScope.Driver/Driver.c)、[Windows checker 说明](https://github.com/darrylmorley/whatcable-windows/blob/main/README.md)。

UCC3 的手册提供了有价值的限制说明：线材测试时，两端接入测试仪；电阻结果包含接触电阻；主动线材不支持常规导通检查，但可读 e-marker。由此可以看出，即使加入测试硬件，也需要按线材类型决定适用的测试，不能把无法测试直接显示为损坏。[UCC3 官方手册](https://bit-trade-one.co.jp/adusbcim3/jpnmanual/)。

对 Windows 产品而言，第一项技术验证应该是“这台电脑开放了哪些数据”。微软提供的 USB Hub 查询接口适合枚举设备与读取连接速度；Type-C / PD 则涉及 UCSI 和固件。微软的 UCSIControl 测试工具还要求启用默认关闭的测试接口，因此“开发机能读出”并不等于“普通用户安装应用后就能读出”。[USB 速度接口](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/usbioctl/ns-usbioctl-_usb_node_connection_information_ex_v2_flags)、[微软 UCSI 文档](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/ucsi)。

Linux 有较清楚的 Type-C 信息路径：`/sys/class/typec/` 可以呈现端口、连接对象以及可选的线材/插头对象。但内核明确依赖端口驱动注册这些信息，因此某台机器没有 cable/identity 信息时，不应把“系统未提供”解释成“线材没有芯片”。[Linux Type-C 文档](https://docs.kernel.org/driver-api/usb/typec.html)。

USB-C 的插头形状、数据速率与供电等级应该作为不同字段。USB-IF 的认证标识也分别表达功率与数据能力；USB 2.0 C-C 线同样可以属于高功率线材类别。产品界面不宜只写含义不清的“USB-C 线”或“USB 3.2”，应优先展示明确的 Mbps/Gbps、额定功率，以及这些数值的数据来源。[USB-IF 线缆标识要求](https://www.usb.org/cable_connector)。

根据这些证据，我建议将第一版定位为“连接诊断与线材规格助手”，并采用以下顺序验证。这是产品建议，不是已有竞品功能清单。

1. **先验证 Windows 数据可得性。** 用不同品牌电脑与已知规格线材，确认设备枚举、当前速度、端口能力、Type-C/PD 信息分别能读到什么，并记录权限与固件条件。
2. **做清楚的证据展示。** 每个结果标明“芯片声明”“当前协商”“本次实测”或“系统未提供”。读取不到时保留未知，避免自动填成低规格。
3. **提供引导式故障排查。** 固定电脑、端口与外设，对比已知正常线与待测线；必要时再分别换端口、绕过 Hub。吞吐测试必须标明整个连接组合的表现。
4. **把质量指标拆开。** 初期可以报告断连次数、传输验证结果、当前协商状态；电阻、压降与高速信号完整性要由相应硬件测试提供证据。
5. **评估可选硬件扩展。** 如果用户真正需要清点一箱线材、检查断芯或评价充电损耗，可接入测试模块；采购前确认通信协议、数据导出和授权条件，不能默认商业仪表开放了所有功能 API。

建议的验收样本至少包含：USB 2.0 C-C 线、高速 C-C 线、不同功率等级线材、A-C 线、主动雷电线；并加入“高速线连接低速外设”“经过 Hub 降速”“线材规格读取失败”这些反例。测试目标是验证提示是否诚实、定位是否有依据，同时衡量实际覆盖率。

值得优先投入的方向是：Windows 上面向普通用户的解释与排查流程，以及统一呈现线材声明、链路状态和实测结果。是否还有足够市场空间，需要后续访谈和实机测试；本轮没有调查用户付费意愿，也没有据此估算市场规模。
